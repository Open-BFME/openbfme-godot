# OpenBFME text catalog (L10N-1)

Retail text (unit names, menus, the campaign) comes from the player's own CSF files and stays there. This catalog holds the text
**OpenBFME adds**: the launcher, and (milestone 2) the engine's and the game scripts' own screens, errors and options.

## Files

| Path | What |
| --- | --- |
| `tools/l10n/catalog/en.json` | the source: every id with its English text |
| `tools/l10n/catalog/<code>.json` | one file per language: a subset of en's ids, translated |
| `tools/l10n/l10n.py` | validator, generator, coverage report, id-usage check, hard-coded-English lint |
| `launcher/scripts/l10n/l10n.gd` | the GDScript runtime (copied to `godot/scripts/l10n/l10n.gd` by the generator) |
| `*/scripts/l10n/catalog.gd`, `engine/src/GameClient/OpenBFMETextCatalog.inc` | generated, never edited |
| `engine/src/GameClient/OpenBFMEText.{h,cpp}` | the engine's runtime (same rules) |

Each consumer gets only its own ids: the launcher `launcher.*`, the game `game.*`, the engine `engine.*`, all of them `common.*`.

## Format

A flat JSON object per language (the "key-value JSON" that translation tools such as Weblate read):

```json
{
  "@@locale": "en", "@@name": "English", "@@status": "source",
  "launcher.settings.title": "Settings",
  "launcher.aio_install.listed_twice": "{package} lists {file} twice.",
  "launcher.mods_screen.count": {"one": "{count:d} mod", "other": "{count:d} mods"},
  "@launcher.settings.title": {"description": "optional note for translators (en.json only)"}
}
```

- **Metadata**: `@@locale` (the file's code), `@@name` (the language's own name, shown in Settings), `@@status`: `source` (en only),
  `complete`, `partial`, or `sample` (a few strings to test the path; Automatic never picks a sample).
- **Ids**: lower-case, dotted, stable: `<consumer>.<area>.<name>`; the area is the screen or the script's file name (`launcher.main.*`,
  `launcher.updater.*`). An id never changes meaning: new wording that needs a new translation gets a new id.
- **Placeholders** are named and typed: `{name}` text, `{name:d}` integer, `{name:.Nf}` a number with N = 0..3 decimals, written with
  the language's decimal separator (1,5 in German). `{{` and `}}` are literal braces; any other brace is a validation error. A
  translation has exactly the placeholders (names and types) of the English text, in any order. The message is read once: an
  argument's text is never read again, and a `%` is plain text (FMTSTR-2's rule for localized text: a translated string is never a
  format string).
- **Plurals**: the value is an object of the language's CLDR categories for whole numbers (`one`/`other` in English and German,
  `one`/`few`/`many` in Polish and Russian; the table is `PLURAL_CATEGORIES` in `l10n.py`, mirrored in both runtimes), selected by the
  integer argument `count`. A form may leave `{count}` out ("one mod"). A language with no rule in the table cannot be added until it has one.
  Gender is not needed by any current message; a message that does gets one id per form.

## Missing text (no silent default, PLAN rule 10)

- An **unknown id**, a **missing argument** or **one of the wrong type** is an error: the runtime reports it (`push_error` in GDScript, the
  `errors` list or stderr in C++), keeps it visible in the text (`{name}`, the id itself), and the tests fail on it. `l10n.py check`
  finds unknown ids and wrong argument names statically (every `L10n.t("id", {...})` call with a literal dictionary is checked).
- A **missing translation** of an existing id shows the English source: that is the defined behaviour of a partial translation, and
  `python3 tools/l10n/l10n.py coverage` lists every such id per language. A `complete` file must have no missing id (tested).

## Language selection

The launcher's Settings > General > Language: **Automatic** (the default) or a catalog language. Automatic uses the retail install's
language, read from its `lang/<Language>.big` archive (the archive the game mounts; RetailArchivePolicy.cpp), when OpenBFME has a
`complete` or `partial` translation of it, else English; the Settings item says which and why ("Automatic (English: OpenBFME has no
Polish translation yet)"). A pick is stored in the launcher's state (`launcher/language`) and applies at the next start. Test runs
take `--language=<code>`. Milestone 2 shares the pick with the game's Options.

## Checks (`tools/l10n/test_l10n.py`)

The catalog validates; the generated files are current; every id the code uses exists with the arguments its placeholders need; every
id is used; the GDScript and C++ runtimes pass the same cases (`launcher/tests/l10n_test.gd`, `engine/tests/test_openbfme_text.cpp`);
and the **lint**: no string literal in `launcher/scripts` that looks like player-facing English, outside log/debug calls, dictionary
keys, paths and protocol matching. A literal that must stay (a product name, a theme name, protocol text) is listed with its reason in
`tools/l10n/lint_allow.json`; an entry that no longer occurs fails the test too.

## Writing code

```gdscript
const L10n := preload("res://scripts/l10n/l10n.gd")
label.text = L10n.t("launcher.settings.title")
_set_status(L10n.t("launcher.updater.downloaded", {"name": asset, "size": mb}))     # "{name}: {size:.1f} MB"
```

- Put whole sentences in the catalog, never fragments glued with `+` (a translation needs the whole sentence to order its words).
- Never `%`-format a translated string, and never build an id at run time from data (a table of ids as literals is fine: the check
  finds them).
- Text goes through `L10n.t` when it is shown, not in a `const` or a `static var` (those are made before the language is chosen).
- Logs stay English where they are only logs (`Log.line("LAUNCHER ...")`); a message the player sees is translated even when it is
  logged too.
