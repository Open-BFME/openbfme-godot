# RW 0x942733 — command availability (S-850, S-290)

## Evidence and scope

Recovered from the supplied RotWK disassembly, with the RotWK-to-BFME2 map
and the byte-matched donor sources cited below. **Partial recovery**, not a
byte-matched replacement or a claim that S-850 is closed. The supplied image
has `stxt*`, `.mackt` and `.danetta` sections: PLAN rule 9 / S-001 still applies.
No execution trace establishes clean-retail parity. No binary or raw pack is
part of this document.

The function is ControlBar's command-availability evaluator (ZH term:
`getCommandAvailability`), not a hero-record update. It takes a command button,
window, object, output progress pointer, and a recursion flag. The exact original
RotWK C++ spelling is **INFERENCE**. The five arguments and callee-cleaned stack
are established by the disassembly. It writes `1.0f` to the output before any
early exit (RW 0x942740; constant RW 0xBD1908 checked in the supplied image).

### Callers / when it runs

* RW 0x9312B9 calls at 0x931370: mapped donor
  `AptInGameSpellBookInterface::Impl::Update` (donor not byte-matched).
* RW 0x71CB0D calls at 0x71CCB0: mapped donor
  `ControlBar::rva0031B210`, special-power shortcut update.
* RW 0x94397F at 0x943ADB and RW 0x944911 at 0x9449D6: command-window updates.
* RW 0x940435 at 0x9405B3 / 0x940625: command processing, before executing a press.
* Recursive call at RW 0x9428B5: determines whether a disabled object's button
  would otherwise be hidden; it does not unconditionally hide disabled commands.

## Recovered C++ fragment: REVIVE

This fragment is **only** the switch arm; common gates above must run first.
`rva0037E7A5` and `rva0037E898` are the donor spellings in
`Code/GameEngine/Source/Common/Rva0037E421Accessor.cpp`. Their mapped RotWK
bodies are RW 0x780C2F and RW 0x780D22; the latter is tier B, not identical.
`getLocalPlayer` / `isLocallyControlled` receiver identification at RW 0x6A8803
still needs independent typing; it is represented explicitly rather than guessed.

```cpp
// RW 0x942ECF..0x942F69; descriptive names for unresolved receiver types.
if (!playerListQuery_6A8803(object)) return 3;
if (object->isEffectivelyDead()) return 0;
Player *owner = object->getControllingPlayer(); // RW 0x68B678
int index = button->reviveIndex;                // +0xC0
if (!owner || index == -1) return 0;
ThingTemplate *tt = owner->revivalTracker.rva0037E7A5(index);
if (tt && !owner->allowedToBuild(tt)) return 4; // RW 0x6AC856
int canMake = TheBuildAssistant->canMakeUnit(object, 0, index);
if (canMake == 7) return 7;
if (canMake == 6 || canMake == 5) return 0;
if (canMake == 2) return 6;

// RW 0x942F69..0x942FC1. Do not change float-store/compare order.
unsigned cost = 0;
// Conceptual extended return: C++ long double is NOT a portable x87 contract.
long double returned = owner->revivalTracker.rva0037E898(index, &cost, object);
float stored = (float)returned;
*progress = stored;
if (returned == 0) return 0;
if (stored != 1.0f) return 5;
return owner->money < cost ? 6 : 1; // unsigned comparison
```

The zero and one comparisons also treat unordered as unequal (the parity tests
at RW 0x942F93 / 0x942FA9). The existing port's early `startFrame >= 0` →
NotReady is not this algorithm: at zero progress retail disables; canMakeUnit
runs before progress; a rounded progress of exactly one is tested against money.

## Follow-up recovery and port

The following helper behavior is now established from the target instructions,
not inferred from address-shaped donor names:

* RW 0x942490 (tier-A donor `ControlBar::rva0053BA87`) compares the button's
  `DisableOnModelCondition` (+0x1E0) and `EnableOnModelCondition` (+0x194) against
  Object's model conditions (+0x10C). RW 0x6632E9 is an ANY intersection across
  19 words, not containment of all bits. A disable intersection wins; an empty
  enable mask imposes no requirement. Return 3 makes the caller **restrict**,
  not hide. Only command 0x18 skips this helper.
* RW 0x9325B4 tests whether the disabled mask is nonempty; RW 0x8C2233 counts
  its set bits. The sole `DISABLED_TEMPORARILY_BUSY` bit (8) is ignored. Other
  masks recurse with the final argument true, except EVACUATE, CREW_EVACUATE,
  EXIT_CONTAINER, BEACON_DELETE, SET_RALLY_POINT and SWITCH_WEAPON. Preserve a
  hidden recursive result; every other result becomes restricted.
* Object +0x457 bits 0/1 are SCRIPT_DISABLED / SCRIPT_UNPOWERED; disabled bit 5
  is DISABLED_UNMANNED. These **hide**, before the exceptions above. A missing
  experience tracker or insufficient positive `RequireLevel` also hides.
* RW 0x75CDC4 is an ANY intersection across **four** words: Object status
  (+0x94) against SpecialPowerTemplate `PreventActivationConditions` (+0x64).
  RW 0x6AC25F / 0x6AC287 are disabled/hidden **science-list** queries, not
  upgrade queries. The special-power branch chooses the first owned required
  science; no owned science hides, while a disabled/hidden selected science
  restricts. `ShowButton` false hides.
* RW 0x6AAC52 tests Player +0x35A and +0x754 for zero (the donor uses +0x33A
  and +0x734). The port currently combines defeated-player state; it does not
  recover two independently writable flags from this helper alone.
* RW 0x780D22 is **not** the production-progress getter RW 0x780C9F. An idle
  record writes its cost when the pointer is non-null and returns one. An
  active record leaves the cost output untouched; positive duration returns
  `(unsignedFrame - signedStartFrame) / duration` in x87 PC24 order. A missing
  record or nonpositive active duration returns zero. In contrast, 0x780C9F
  returns zero for idle and one for nonpositive active duration.

`ControlBar::evaluate` now applies the recovered common gates, including to
REVIVE buttons instead of bypassing them. `PlayerHeroList::availabilityAt`
ports 0x780D22 without changing the production getter. REVIVE runs canMakeUnit
before the availability query, distinguishes zero progress from nonzero
progress, compares the stored float with one, then uses unsigned money/cost.
The idle timer is not drawn; this presentation does not change the query's
returned one. Empty NeededUpgradeAny lists now restrict, matching the final
flag test at RW 0x942989. All new calculations are display reads, not simulation
state updates; no pinned vector is changed.

S-850 remains open. **Not implemented:** the second REVIVE placement pass,
local-player/observer receiver selection and command-center substitution,
Object +0x45B, AI option 0x40000000/vslot 0x228, option 0x800's castle scan,
remaining command-specific arms in the inventory above, special-power horde
unit-count / substitute-button / CommandTrigger / BattlePlan rules, and exact
availability 4/7 presentation (still Restricted). The owner relationship gate
of RW 0x6A8803 is not an independent new spectator UI path: the current HUD
populates only locally controlled command sets. Create-A-Hero image, live hero
side list and radius cursor are separate S-850 gaps.

Regression coverage: `rotwk-c availability*` in `test_hero_hud.cpp` drives the
retail HUD's rank/script/disabled/model/ShowButton gates and separately tests
idle, zero, partial, exact-one and zero-duration hero availability. The existing
`hero hud*` test exercises recruitment and ability casting end to end through
the engine HUD. These are retail-backed engine tests, not clean-retail process
comparison or rendered Godot captures.

## Follow-up: special-power readiness (RW 0x9434F7..0x9435EA)

The modified-executable provenance caveat above still applies. A second pass
through the supplied disassembly corrects the earlier port's interpretation of
the SPECIAL_POWER model-condition exception: it skips only the pre-switch
check, not the calls at RW 0x9435C3 (recharging) and 0x9435DC (ready).
Either late check can return disabled availability 0, represented as Restricted.

Recovered control flow after the unresolved substitute-button lookup:

```cpp
// RW 0x9434F7..0x943564: the trigger scan has no different return value.
if (!module) return COMMAND_AVAILABLE;
// RW 0x943569..0x94357A: virtual +0x48, called with a null target.
if (!module->isUsable(nullptr)) return COMMAND_DISABLED;
// RW 0x94357A..0x9435D2; interface +0x0C is RW 0x6519A6:
// signed pause count at module +0x1C > 0.
if (!module->isReady()) {
    float progress = module->getPercentReady();
    if (!(progress > 0) && module->isPaused()) return COMMAND_DISABLED;
    return modelConditionsAllow(button, object) ? COMMAND_NOT_READY : COMMAND_DISABLED;
}
// RW 0x9435D7..0x9435EA, before the remaining update/BattlePlan gates.
if (!modelConditionsAllow(button, object)) return COMMAND_DISABLED;
```

The port now reproduces these late model checks, positive versus zero paused
progress, and the missing-module enabled result. Tests exercise retail Athelas
ready/recharging/paused states and a retail fighter without an Athelas module.
This changes HUD reads only; no expected simulation vectors are edited.

**Still blocked, not treated as equivalent:** virtual +0x48 is RW 0x897E01,
which calls RequirementsFilter (RW 0x8969E5), the heal/recent-damage guard
(RW 0x896DB4), and an update interface's target gate. The current port only has
the filter portion of this predicate. Special-power update substitution,
the update interface gate and BattlePlan must be recovered/ported before the
whole command arm can be claimed complete. The missing-module result above
does not claim to implement the earlier substitute lookup.

## Remaining prerequisite audit: receivers and command arms

RW **0x6A8839** maps to `BfmeThingRV::bfmePickRV`
(Common/BfmeThreeHundredTwentyFour.cpp). The target reads the primary player
at receiver +0x10, returns null if absent, and calls RW 0x6AAC52. When that
predicate is false, a nonnull ControlBar and its player pointer **+0x218**
override the primary player; otherwise the primary player is returned. The
BFME2 field is +0x210, not the RotWK offset. Calling this simply "local
player" loses a real branch. Calling it an observer player is still
**INFERENCE** until its writers and the two player flags are integrated.
The current HUD has no corresponding independently selected display-player
field and populates only locally controlled command sets.

Command 0x20 substitutes RW **0x6AD0D9**, `findNaturalCommandCenter`.
Its tier-A callback RW **0x6AD07B**, `doFindCommandCenter`, accepts the first
COMMANDCENTER whose template's default owning side matches the player and
which is neither UNDER_CONSTRUCTION nor SOLD. Command 0x26 instead calls
RW **0x6AD0F8**, `Player::rva002AC629`: its tier-A callback RW **0x6AAE3C**,
`doFindRva002AC629`, tests template byte +0x117 bit 3 and controlling-player
identity, then the query caches an ObjectID. These are different finders.
The latter bit's game-level name is not established by that callback alone.

Both finders use the player's ordered object traversal. The port's global
GameLogic object chain and TeamFactory's creation-order containers are not a
demonstrated equivalent of the player's prototype/team/object walk. There
is no `Player::iterateObjects` or corresponding finder-cache lifecycle in
the port. Choosing the first matching global object could silently switch
the receiver when several command centers exist. The prerequisite is the
ordered player traversal/cache lifecycle plus the ControlBar display-player
state, not a fallback to the selected object.

explicit. These are dependencies/recovery gaps, **not** fully ported arms:
