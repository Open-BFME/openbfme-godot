# RW 0x751263 — AIAttackState::update's victim block (PORT-14, S-7184)

`AIAttackState::update` is RW **0x7510EC .. 0x7515E1**, slot 6 of vtable **0xC2A1D8**
(`0xC2A1D8 + 0x18 = 0x7510EC`; the constructor RW 0x74CABC installs the table at
RW 0x74CAEA, the destructor RW 0x74CB56). The neighbours are onEnter `+0x10`
(RW 0x74CED6) and onExit `+0x14` (RW 0x74D25D). STOPS S-583 names the same function
from the crush-attack side. Every address below is an instruction address in the
2.01 `game.dat` (S-001's community-image caveat applies); names taken from the BFME2
decompilation or from the port are marked INFERENCE, the instruction and the field
offset are not.

Registers: `edi = this`, `ecx = [edi+0x18]` (the main machine), `esi = [ecx+0x14]`
(the owner), `ebx` and `[ebp-8]` the main machine's goal object, `[ebp-0xC]` the
owner's AI, `[ebp-0x10]` `lastCommandSource`, `[ebp-1]` the owner's status 0x1C
IS_MELEE_ATTACKING, `[ebp-2]` `relationship == ENEMIES`.

Returns: RW 0x751227 `push -2; pop eax` = STATE_FAILURE, RW 0x751456 `or eax,-1` =
STATE_SUCCESS, RW 0x7515DA `xor eax,eax` = STATE_CONTINUE, RW 0x7515D4
`jle 0x75122A` passes a non-positive inner-machine result through. RW 0x7515E1 already
begins another function.

## The dead-victim path (RW 0x751438 .. 0x7515DA)

RW 0x751438 .. 0x751440 calls AI vslot `+0x240` and does **not** end the attack.
RW 0x751446 .. 0x751456 tests KindOf ARMY_OF_DEAD (owner template `+0x11A` bit 0x80) and
returns STATE_SUCCESS for it; every other owner leaves through RW 0x751450 `je 0x7515C8`,
the inner attack machine's update. RW 0x7515C8 .. 0x7515CF is machine vslot `+0x10`
(`AIStateMachine::updateStateMachine`, RW 0x751D34): a result <= 0 is returned unchanged
(0x7515D4 `jle 0x75122A`), a positive sleep becomes STATE_CONTINUE (0x7515DA
`xor eax,eax`). This is what keeps a charge state's next target and a wind-up's pending
shot alive after the victim dies (STOPS S-583).

There is **no** `replacementVictim()` / `notifyNewVictimChosen()` call anywhere in
RW 0x7510EC .. 0x7515E1: horde-member selection happens in `Object::adjustVictim`
(RW 0x68D30E) from onEnter and from the target searches.

## What the port does, and what it does not

`AIAttackState::update` takes the RW shape: `rwVictimGone` (RW 0x75126D .. 0x75128E,
without `CombatQueries::isAlive`), ARMY_OF_DEAD -> STATE_SUCCESS, otherwise the inner
machine through the new `updateAttackMachine()`; the special non-enemy path with
`clearGoalAndTeamTarget()` (RW 0x6627F0(0), `AIHuntState::teamTarget` as the port's
resolve of RW 0x7A3E36, `setTeamTargetId(0)`); `setCurrentVictim`; the empty-garrison and
ENEMIES test of RW 0x751334 .. 0x7513B7 (RW probes an empty, non-CAN_ATTACK
garrisoned victim first, but that probe and 0x75136E .. 0x751385 both end at
0x751387 for every relationship other than ENEMIES, so the port tests the
relationship alone); the goal sync of RW 0x7513BC. The ZH donor's
`replacementVictim()` / `notifyVictimIsDead()` branches are gone, and the parent no
longer repeats the stealth test (lane STEALTH-1): RW reads the stealthed, undetected
victim in the attack sub-state RW 0x752382 .. 0x7523B2, which the port's aim state
carries.

Not ported (STOPS S-7184): the tail RW 0x7513D1 .. 0x751488 (contain vslot `+0xC0`
isPassengerShotBlocked RW 0x865B33, the full chooseWeapon body RW 0x742D63, the
locked-weapon name compare, the shot-limit gate), RW 0x751488 .. 0x7515B3 (the melee
machine's onExit / onEnter and the setState of machine `+0x1C`), and the prelude
RW 0x7510EC .. 0x7511DC (the vision / attack-position test and the temporary speed-cap
reset RW 0x742DFC, an INFERENCE name). The port's `m_victimTeam` keeps a team id where RW
state `+0x2C` holds a `Team*`, and RW never rewrites it in update.

Tests: `engine/tests/test_port_14.cpp` (`PORT-14*`), one case per branch above plus the
version 1 / version 2 snapshot of state `+0x49` (`AIAttackSnapshot.cpp`).

## A port finding: the BFME2 Rivendell mission (2026-11-12)

The block is measured against `engine/tests/test_bfme2camp1.cpp` (lane BFME2CAMP1, which
pins retail's own outcome for `MAP GOOD Rivendell`). On `upstream/main` all 43
`bfme2camp1*` cases pass; with this block the first one (`... plays from its start to its
first objective ...`) fails: Glorfindel reaches objective 1 at frame 641 instead of 650
and `m.unit("First recruit")` is null, i.e. the Lorien recruit horde that retail keeps
alive is destroyed. The shift is reproducible in a filtered run and does not depend on
the rest of the suite.

Probe: keeping the port's `notifyVictimIsDead()` (the vslot `+0x240` stand-in that clears
AI `+0x40`) before `updateAttackMachine()` gives frame 641 again, so a stale current
victim is not the cause; the dead-victim hand-over itself is. The unported remainder is
therefore load-bearing rather than cosmetic: RW 0x7515BC (the inner state's failure test,
S-7164) and the tail RW 0x7513D1 .. 0x7515B3 sit between the parent's choice of return and
what the AI does with it, and this port's inner states answer a dead victim with SUCCESS
(approach) or FAILURE (aim / fire, S-7175) - a mix the RW parent may shape differently.
The fork has carried the same code since 2026-11-07 with this test unchanged, so the
divergence is a fork regression that this lane surfaced, not an upstream-only effect.

Until RW 0x7515BC and the tail are read, S-7184 keeps the row open and the block is not
offered upstream.
