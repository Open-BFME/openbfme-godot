# RW 0x90CE35 — resolve a Player's GameSlot by name key

> Restored research; port disposition reconciled with current main STOPS.md
> (archive snapshot 1eea93ac66). The 2026-10-23 function map classifies this
> entry as RotWK-only. Historical target reconstruction below is UNVERIFIED

## Identity and callers

S-415. Free/cdecl helper taking Player*, returning GameSlot*, no receiver.
The original symbol is unknown (`findPlayerSlot` below is **INFERENCE**).
TheGameInfo is RW 0xDE892C; NameKeyGenerator is RW 0xDD90E4. Player +0x50 is
the name key; GameSlot +0x34 is the string converted by NameKeyGenerator.
Calls RW 0x800B55 (GameInfo::getSlot, GameInfoGetSlot.cpp) and RW 0x49F474
(NameKeyGenerator::nameToKey, NameKeyGenerator_nameToKey_ascii.cpp) are
byte-matched donors. No float or RNG, and no patched-section calls; S-001
provenance caveat still applies.

Call sites from the pack: RW 0x90CEC2 in 0x90CE76 (unit-builder selection),
0x9A10FA in 0x9A10D8, 0x9BCB4E in 0x9BCA8E, 0x9BC737 in 0x9BC734,
0x9B3DC5 in 0x9B3D8B, 0x9B4425 in 0x9B43E9, and 0x9BC895 in 0x9BC882.
The existing port also cites this lookup for player-start tactical decisions
and fortress rebuilding. It is shared infrastructure, not a unit queue method.

## Recovered C++

```cpp
// RW 0x90CE35..0x90CE74
GameSlot *findPlayerSlot(Player *player)
{
    if (!TheGameInfo) return 0;
    for (int slotIndex=0; slotIndex<8; ++slotIndex) {
        GameSlot *slot = TheGameInfo->getSlot(slotIndex);
        NameKeyType key = TheNameKeyGenerator->nameToKey(slot->m_name34);
        if (key == player->m_nameKey50) return slot;
    }
    return 0;
}
```

Exactly eight slots, first matching key wins. No player-null or slot-null
check, no player-index comparison, no occupancy/team/faction test. A missing
global returns null without converting any names. A miss converts all eight
names. Use the exact nameToKey semantics, not a case-folded string comparison
or the name key supplied by an unrelated player-template field.

## Historical port / current S-415 disposition

The old branch integrated this runtime mapping, but current main does not:
base initialization still reads Player's cached start index, and fortress
rebuilding reads Player's own template (the S-413 inference in STOPS.md).
The old implementation and test description below are historical, **not a
claim that this branch has ported or verified them**. Reapplying that code is
blocked pending a verified RotWK image: the new map calls RW 0x90CE35
RotWK-only; CreateMPPlayers (RW 0x627C1F, BFME2 RVA 0x23EE5B,
`GameLogic/System/GameLogicInit.cpp`) and home point (RW 0x90CE76,
BFME2 RVA 0x506CF5, `Common/Rva00506CF5HomePoint.cpp`) are tier B
same-shape and require `pair_diff.py`. The tier-A fortress donor is
`GameLogic/SkirmishAI/AIBaseBuilder/AIBase_DoXfer.cpp`,
`AIBase::buildFortressIfNeeded`, BFME2 RVA 0x5ADAB2; it does read the
slot's template, but does not prove the RotWK-only slot lookup itself.

Historical evidence: RW 0x627C1F's first loop writes each
occupied slot's ASCII side name at +0x34 (assignment RW 0x627CEB..0x627CF2).
For skirmish mode 3 and template >= 0, RW 0x627CC9 formats `Player_<start+1>`;
negative templates use `Observer_<slot+1>`. The second loop uses that same
field as the side dictionary's playerName (RW 0x627DC0..0x627DE7), which feeds
Player +0x50 through PlayerList initialization. The existing `SkirmishSides`
implementation already constructs these exact names; they are **not** the
Unicode lobby display names. Campaign/living-world naming branches remain
outside the skirmish path.

In that old port, `LiveGame` retained the resolved setup and those names in
`GameLogic` before the AI initialized. `findGameSlot` invoked the shared NameKeyGenerator for
each name in order (RW 0x49F474 is the AsciiString adapter to RW 0x5487EC),
including empty or closed slots. Reset removed the runtime GameInfo; saves
reconstructed it from their recorded setup through the normal start path.
No wire-format field or native snapshot serializer was invented.

The base start-position lookup (RW 0x90CE76) and fortress rebuild's template
lookup (RW 0x9BC895..0x9BC8A4) used the returned slot rather than the
Player's cached start/template. A missing slot in AI initialization is
reported; the fortress caller's retail null dereference became an explicit
error rather than a silent fallback.

The old branch's retail tests covered normal population, duplicate first-match even when closed,
slot 7, case-sensitive miss, absent GameInfo, and a base whose slot start
differs from the Player's cached start. Ordinary valid skirmishes should not
change simulation results; divergent slot/player metadata deliberately uses
the retail slot. Pinned vectors remain untouched.

The old port closed only the runtime slot/name-key subgap, **not all S-415**.
The unit builder's extra hero entry at RW 0x9A1104 tests slot +0x50, whereas
the current Create-a-Hero setup models +0x60/+0x64; their equivalence has not
been established. Living-world behavior remains open. The former "second
unit request" is now identified and ported as AIExpansionScience (AI5,
S-1876), not a remaining unidentified unit request. All historical target
evidence retains the S-001 caveat.
