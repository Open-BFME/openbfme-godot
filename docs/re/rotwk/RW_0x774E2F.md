## 3. `AIGroup::moveFormationToPos` mode 1 (RW 0x77348C) and command `0x25`

`gatherAndMoveInFormation` (RW 0x7747DE) prunes invalid members (RW 0x76FFF0), verifies at
least one member has a `FormationPriority` locomotor, clears goals (RW 0x76F426), computes
the ground path (RW 0x76F115), assigns slots via `createFormation` (RW 0x94FCBA — ignores
its stack arguments), and calls `moveFormationToPos(pos, source, mode, ground, false)`
(RW 0x77348C).

At the end of `moveFormationToPos` (RW 0x773D4D .. 0x773DD1), `mode` (`[ebp + 0x10]`)
selects how each member receives its rotated slot path (`path`) and final slot (`dest`):

```
RW 0x773D4D  if (mode == 1 && unit->isAbleToAttack())    ; RW 0x691269
             {
RW 0x773D66      if (ai->canFollowTeamPath())            ; RW 0x667144
RW 0x773D8C          ai->cmdFollowPathAsTeamAttack(&path, nullptr, angle, source); ; RW 0x77122F (cmd 0x25)
                 else
RW 0x773DA1          ai->aiAttackMoveToPosition(&dest, 0x7FFFFFFF, source);        ; RW 0x696266
             }
             else
             {
RW 0x773DA8      if (ai->canFollowTeamPath())            ; RW 0x667144
RW 0x773DC8          ai->cmdFollowPathAsTeam(&path, nullptr, angle, source);       ; RW 0x7711AF (cmd 0x24)
                 else
RW 0x773DCF          ai->aiMoveToPosition(&dest, source);                          ; RW 0x66C4CA
             }
```

Command `0x25` (`RW 0x77122F` -> `aiDoCommand` `RW 0x66ABAF` -> `AIUpdateInterface` vtable
`RW 0xC10590` slot `+0x80` = **RW 0x66BC68**) is instruction-for-instruction identical to
command `0x24` (`slot +0x7C` = RW 0x66BB9D) except for the state id passed to
`m_machine->setState`:

* Command `0x24` (RW 0x66BC59): `push 0x36` -> state **54** (`AI_FOLLOW_PATH_AS_TEAM`).
* Command `0x25` (RW 0x66BD24): `push 0x3D` -> state **61** (`AI_FOLLOW_PATH_AS_TEAM_ATTACK`).

Neither slot `+0x7C` nor slot `+0x80` is overridden by `HordeAIUpdate`, `DeployStyleAIUpdate`,
or `GiantBirdAIUpdate` (`canFollowTeamPath` RW 0x667144 already excludes air-surface units,
routing them to `aiAttackMoveToPosition` RW 0x696266). `acceptCommand` (RW 0x667174) treats
`0x24` and `0x25` identically.

## 4. State 61 in `AIStateMachine` and `AIFollowPathAsTeamState`

In `AIStateMachine`'s base state constructor (RW 0x753755, at RW 0x753B1E .. 0x753B6B),
states `0x36` (54) and `0x3D` (61) both instantiate `AIFollowPathAsTeamState` (size `0x60`,
ctor **RW 0x74FC9B**, vtable **RW 0xC28848**), both with success and failure transitions to
`AI_IDLE` (`0`), differing only in the constructor's second argument `isAttack`:

* State `54` (`0x36`, RW 0x753B27): `AIFollowPathAsTeamState(machine, /*isAttack=*/0)`.
* State `61` (`0x3D`, RW 0x753B4E): `AIFollowPathAsTeamState(machine, /*isAttack=*/1)`.

### Sub-machine `AIAttackMoveStateMachine` (RW 0x74E083)

Shared with `AIAttackMoveToState` (RW 0x755720) and `AIAttackFollowWaypointPathState`
(RW 0x750AE7, already ported in `AIWaypointPath.cpp`):

* `0` (`AI_IDLE`): `HuntIdleState` (`makeHuntIdleState`, scans every 5 frames).
* `0x27` (39): `AIAttackPickUpCrateState` (unported across the engine, S-1188 / S-1189).
* `50` (`AI_ATTACK_OBJECT`): `AIAttackState(machine, /*follow=*/false, /*attackingObject=*/true, /*force=*/false)`, transitioning to `AI_IDLE` on success or failure.

Note on RNG determinism: retail builds the sub-machine in the state's constructor (RW 0x74FC9B, then its vslot `0x1C`).
The port's `HuntIdleState` draws the logic generator on every entry, so the port builds the machine on the first
`onEnter` instead (INFERENCE, a port choice: the pattern of `AIAttackFollowWaypointPathState` in `AIWaypointPath.h`);
every entry then draws exactly once, with a new or a reused machine, and a loaded game draws as a continued one.

### Vtable `RW 0xC28848` methods affected by `+0x5C`

* **`onEnter` (vslot `0x10`, RW 0x74FD39)**:
  * If `m_attackMachine`: `clear()` and `setState(AI_IDLE)` (`0`).
  * Saves `m_savedCommandSource = ai->getLastCommandSource()` (AI vslot `0x23C`; `+ 0x60` takes the angle `[ai + 0x1A0]`).
  * Runs the base path setup and starts the first segment (`startMove`, RW 0x74FA00).
* **`onExit` (vslot `0x14`, RW 0x74B800)**:
  * If `m_attackMachine`: `setState(AI_IDLE)` (`0`) so any active `AIAttackState` exits cleanly.
  * Runs base `onExit` (RW 0x74FAF2: exits internal move, clears pathfinder goal and path).
* **`update` (vslot `0x18`, RW 0x74FF49)**:
  * Local flags: `retarget = false`, `justFinishedAttack = false`.
  * If `m_attackMachine` is non-null:
    1. **Active engagement (`currentStateId != AI_IDLE`, RW 0x74FF74 .. 0x74FFDB)**:
       * If parent `machine().goalObject()` (RW 0x8DBACE) is non-null and differs from
         `m_attackMachine->goalObject()`, syncs `m_attackMachine->setGoalObject` (`vslot 0x38`).
       * Calls `m_attackMachine->updateStateMachine()` (`vslot 0x10`).
       * If `m_attackMachine->currentStateId() != AI_IDLE`, returns `STATE_CONTINUE` (`-2`).
       * Otherwise (`AIAttackState` just returned to `AI_IDLE`): restores
         `ai->setLastCommandSource(m_savedCommandSource)` (RW 0x6627F0) and sets
         `retarget = true`, `justFinishedAttack = true`.
    2. **Idle target scan (`currentStateId == AI_IDLE`, RW 0x74FFDD .. 0x750055)**:
       * Calls `victim = ai->getNextMoodTarget(!retarget, false)` (RW 0x66844A: throttled by
         the mood timer while marching, immediate `calledByAI = false` right after finishing
         a kill).
       * If `victim != nullptr`: calls `ai->mover().endingMove()` (RW 0x6627CB: clears
         `m_path` and `m_isBlockedAndStuck` without resetting state 61's `m_index` or parent
         `m_goalPath`), sets `m_attackMachine->setGoalObject(victim)`, enters
         `m_attackMachine->setState(AI_ATTACK_OBJECT)` (`50`), sets
         `ai->setLastCommandSource(CMD_FROM_AI)` (`2`), and returns `STATE_CONTINUE`.
  * **Post-attack repath along the team path (RW 0x7502E0 .. 0x7502ED -> 0x7500F0)**:
    * Runs the segment move (`m_move->update()`, RW 0x74280E).
    * Normally `status == STATE_CONTINUE` jumps to `WaitForOthers` / return `STATE_CONTINUE`;
      when `justFinishedAttack` is true (`[ebp - 1] != 0` at RW 0x7502E9), it jumps instead to
      `RW 0x7500F0`: `status` is `STATE_CONTINUE` (not `STATE_SUCCESS`, so `m_index` is not
      incremented at RW 0x7500FA), passed waypoints are skipped (`RW 0x750108 .. 0x750284`),
      and `startMove` (RW 0x74FA00) computes a fresh path from the unit's post-combat position
      back to waypoint `m_index`.
* **`isAttack` / `isActive` (vslot `0x24`, RW 0x7427EA)**:
  * Returns `m_attackMachine != nullptr && m_attackMachine->currentStateId() != AI_IDLE`.
  * Queried via `AIUpdateInterface` vslot `0x1BC` (RW 0x662B3C -> `currentState()->vslot_0x24`),
    e.g. so a fighting horde in state 61 is recognized as attacking by ally give-way checks
    (RW 0x66DB00).
* **`xfer` (vslot `0x0C`, RW 0x742721)**:
  * Version `1`, base `xfer` (RW 0x7426D0), `m_savedCommandSource` (`+0x58`), `bool hasMachine`,
    and if `hasMachine`, `xferSnapshot(m_attackMachine)`.

## 5. Donor vs RotWK deltas

* **Generals / Zero Hour**: `AIData` has neither `UseFormations` nor `AttackMoveUsesFormations`;
  `AIGroup::groupAttackMoveToPosition` sends individual per-unit `aiAttackMoveToPosition` /
  `aiMoveToPosition` orders, and states 54 / 61 do not exist.
* **BFME2 vs RotWK 2.01**: Same architecture (`AIGroup::gatherAndMoveInFormation` mode 1 ->
  command `0x25` -> state 61 `AIFollowPathAsTeamState(..., true)` with `AIAttackMoveStateMachine`);
  RotWK `AIData` shifts `AttackMoveUsesFormations` to `+0xBA` and `UseFormations` to `+0xBD`;
  both editions ship `AttackMoveUsesFormations = Yes`, so retail enables the formation attack-move
  while the constructor default is also the enabled value.
