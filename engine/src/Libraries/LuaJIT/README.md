# LuaJIT

The VM of lua-gdextension and of the `bfme.*` API (lane LUAGD-1). Retail scripts still run on Lua 4.0.1 (`engine/src/Libraries/Lua`).

Pristine upstream source: `engine/thirdparty/luajit-18b087cd2cd4/`, a `git archive` of
https://github.com/LuaJIT/LuaJIT.git at `18b087cd2cd4ddc4a79782bf155383a689d5093d` (the commit lua-gdextension 0.8.2 pins;
`.relver` holds its commit time, as `git archive` writes it), without its HTML manual (`doc/`, https://luajit.org). Never edited.
Copyright and MIT licence: its `COPYRIGHT`.

- `cmake/LuaJIT.cmake` and `cmake/LuaJITBuild.cmake` build it with its own makefile (macOS, Linux, iOS) or `msvcbuild.bat`
  (Windows) from a copy in the build folder, with `LUAJIT_ENABLE_LUA52COMPAT`, into a static library.
- `prefix.h` (generated by `python3 tools/luajit_prefix.py`; run it again after an upstream update) renames LuaJIT's public
  names (`lua_*`, `luaL_*`, `luaopen_*`, `luaJIT_*`) to `objit_*`. They are the retail Lua 4 VM's names, and both VMs are linked
  into the same library. The LuaJIT build and every file that includes a LuaJIT header are compiled with it first.
- `sol_bridge.h` is forced into lua-gdextension's files in place of `prefix.h` alone: sol2's Lua 5.3 compatibility layer
  redefines a few LuaJIT functions as macros calling the original name; the header gives those names internal forwarders.
- `godot_cpp_compat.h`: godot-cpp 10 keeps `Ref<T>` in `ref.hpp`; lua-gdextension expects it from `ref_counted.hpp`.

The `bfme.*` runtime (`BfmeLuaRuntime.cpp`) switches LuaJIT's JIT compiler off in its state: its execution budget is an
instruction-count hook, and LuaJIT does not call count hooks inside compiled code, so a compiled endless loop would escape it.
